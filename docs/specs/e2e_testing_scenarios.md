# E2E (End-to-End) 테스트 시나리오

## 1. 개요
본 문서는 시스템 전체의 비즈니스 흐름을 검증하기 위한 E2E 테스트 시나리오를 정의합니다. 사용자의 실제 사용 경험을 시뮬레이션하여 프론트엔드, 백엔드 API, 데이터베이스, AI 에이전트, 데이터 파이프라인 등 모든 구성 요소의 상호 작용이 정상적으로 이루어지는지 확인하는 것을 목표로 합니다.

---

## 2. 핵심 테스트 시나리오

### 시나리오 1: 신규 사용자 가입 및 첫 암호화폐 거래
- **목표:** 사용자가 가입하여 첫 거래를 완료하는 전체 프로세스를 검증합니다.
- **단계:**
    1. **(FE)** 사용자가 웹사이트에 접속하여 회원가입 페이지로 이동합니다.
    2. **(FE/BE)** 사용자 정보를 입력하고 '가입' 버튼을 클릭합니다. (API: `POST /api/v1/auth/register`)
    3. **(BE/DB)** 백엔드는 사용자 정보를 검증하고 데이터베이스에 저장합니다.
    4. **(FE/BE)** 사용자는 로그인 페이지로 이동하여 가입한 정보로 로그인합니다. (API: `POST /api/v1/auth/login`)
    5. **(BE)** 백엔드는 로그인 정보를 확인하고 JWT 토큰을 발급합니다.
    6. **(FE)** 사용자는 발급받은 토큰을 사용하여 메인 대시보드로 이동합니다.
    7. **(FE/BE)** 대시보드에서 실시간 암호화폐 시세를 확인합니다. (API: `GET /api/v1/ai/data/collect`)
    8. **(FE/BE)** 사용자가 'BTC'를 0.1개 매수 주문을 제출합니다. (API: `POST /api/v1/trading/orders`)
    9. **(BE/DB)** 백엔드는 주문을 접수하고 거래를 체결시킨 후, 결과를 데이터베이스에 기록합니다.
    10. **(FE/BE)** 사용자는 자신의 거래 내역 페이지에서 방금 체결된 'BTC' 매수 내역을 확인합니다. (API: `GET /api/v1/trading/orders`)
    11. **(FE/BE)** 사용자는 자신의 포트폴리오에서 'BTC' 자산이 0.1개 증가했음을 확인합니다. (API: `GET /api/v1/trading/portfolio`)
    12. **(FE/BE)** 사용자가 로그아웃합니다. (API: `POST /api/v1/auth/logout`)

### 시나리오 2: AI 에이전트를 이용한 자동 거래
- **목표:** 사용자가 AI 에이전트를 구독하고, 해당 에이전트가 시장 상황에 따라 자동으로 거래를 실행하는지 검증합니다.
- **단계:**
    1. **(FE/BE)** 사용자가 로그인하여 AI 에이전트 목록 페이지로 이동합니다. (API: `GET /api/v1/ai/status`)
    2. **(FE/BE)** 특정 AI 에이전트(예: '고수익 추구형')를 선택하고 구독합니다. (API: `POST /api/v1/subscriptions`)
    3. **(Data Pipeline/BE)** 새로운 시장 데이터(예: 급격한 가격 변동)가 데이터 파이프라인을 통해 시스템에 공급됩니다.
    4. **(AI Agent/ML)** AI 에이전트는 새로운 데이터를 기반으로 ML 모델을 실행하여 'ETH' 매수 신호를 생성합니다.
    5. **(AI Agent/BE)** AI 에이전트는 생성된 신호에 따라 사용자를 대신하여 'ETH' 매수 주문을 시스템에 제출합니다. (API: `POST /api/v1/trading/orders` - by Agent)
    6. **(BE/DB)** 백엔드는 주문을 체결하고 결과를 데이터베이스에 기록합니다.
    7. **(BE/Notification)** 사용자에게 AI 에이전트에 의한 거래 체결 알림을 보냅니다. (Email 또는 WebSocket)
    8. **(FE/BE)** 사용자가 로그인하여 거래 내역과 포트폴리오에 'ETH' 자산이 AI 에이전트에 의해 정상적으로 추가되었는지 확인합니다.

### 시나리오 3: 데이터 파이프라인 및 ML 모델 업데이트 검증
- **목표:** 데이터 파이프라인이 새로운 데이터를 수집/처리하고, 이를 기반으로 ML 모델이 재학습 및 배포되는 과정을 검증합니다.
- **단계:**
    1. **(Data Pipeline)** 외부 거래소로부터 최신 1시간 분량의 거래 데이터가 파이프라인에 의해 수집됩니다.
    2. **(Data Pipeline/DB)** 수집된 데이터는 정제 및 전처리 과정을 거쳐 분석용 데이터베이스에 저장됩니다.
    3. **(ML/AI Agent)** 정해진 스케줄(또는 트리거)에 따라 ML 모델 재학습 파이프라인이 실행됩니다.
    4. **(ML)** 새로운 데이터로 모델이 재학습되고, 기존 모델보다 성능이 우수함이 검증됩니다.
    5. **(ML/BE)** 새로운 모델이 AI 에이전트 시스템에 배포되어 실시간 예측에 사용되기 시작합니다.
    6. **(Monitoring)** 모니터링 대시보드에서 새로운 모델 버전이 활성화되었음을 확인합니다.
    7. **(AI Agent)** AI 에이전트가 새로운 모델을 기반으로 예측을 수행하는지 로그를 통해 확인합니다.

### 시나리오 4: API 동시 요청 및 처리
- **목표:** 다수의 사용자가 동시에 API를 요청했을 때, 시스템이 안정적으로 요청을 처리하고 데이터 정합성을 유지하는지 검증합니다.
- **단계:**
    1. **(Test Tool)** 100명의 가상 사용자를 생성합니다.
    2. **(Test Tool/BE)** 100명의 사용자가 동시에 로그인을 요청합니다. (API: `POST /api/v1/auth/login`)
    3. **(BE)** 모든 요청이 500ms 이내에 성공적으로 처리되고, 모든 사용자가 정상적으로 토큰을 발급받는지 확인합니다.
    4. **(Test Tool/BE)** 각 사용자가 1초 간격으로 10회씩 자신의 포트폴리오 정보를 요청합니다. (API: `GET /api/v1/trading/portfolio`)
    5. **(BE/DB)** 모든 요청이 정상적으로 처리되며, 데이터베이스 부하가 임계치를 넘지 않는지 모니터링합니다.
    6. **(Test Tool/BE)** 50명의 사용자는 'BTC'를 매수하고, 50명의 사용자는 'BTC'를 매도하는 주문을 동시에 제출합니다.
    7. **(BE/DB)** 모든 거래가 원자적으로 처리되어 데이터 불일치가 발생하지 않는지 확인합니다. 거래 후 전체 BTC 수량은 변함이 없어야 합니다.

### 시나리오 5: 구독 서비스 및 결제 프로세스
- **목표:** 사용자가 구독 플랜을 선택하고 결제를 완료하는 전체 프로세스를 검증합니다.
- **단계:**
    1. **(FE/BE)** 사용자가 로그인하여 구독 플랜 페이지로 이동합니다. (API: `GET /api/v1/subscriptions/plans`)
    2. **(FE/BE)** 사용자가 'Premium' 플랜을 선택하고 구독을 신청합니다. (API: `POST /api/v1/subscriptions`)
    3. **(BE)** 백엔드는 구독 정보를 생성하고 결제 프로세스를 시작합니다.
    4. **(FE/BE)** 사용자가 결제 정보를 입력하고 결제를 완료합니다.
    5. **(BE/DB)** 결제가 성공하면 구독 상태를 'active'로 업데이트합니다.
    6. **(FE/BE)** 사용자는 구독 관리 페이지에서 활성 구독을 확인합니다. (API: `GET /api/v1/subscriptions/active`)
    7. **(FE/BE)** 사용자가 구독을 취소합니다. (API: `POST /api/v1/subscriptions/{id}/cancel`)
    8. **(BE/DB)** 구독 상태가 'cancelled'로 업데이트됩니다.

### 시나리오 6: 모니터링 및 알림 시스템
- **목표:** 시스템 모니터링과 알림 시스템이 정상적으로 작동하는지 검증합니다.
- **단계:**
    1. **(Monitoring)** 시스템 메트릭을 수집합니다. (API: `GET /api/v1/monitoring/metrics`)
    2. **(Monitoring)** CPU 사용률이 80%를 초과하는 상황을 시뮬레이션합니다.
    3. **(Alert System)** 알림 규칙에 따라 경고 알림이 생성됩니다. (API: `POST /api/v1/monitoring/alerts`)
    4. **(Notification)** 관리자에게 이메일 또는 Slack 알림이 전송됩니다.
    5. **(Monitoring)** 알림 목록에서 생성된 알림을 확인합니다. (API: `GET /api/v1/monitoring/alerts`)
    6. **(Monitoring)** 문제가 해결되면 알림을 해결 상태로 업데이트합니다. (API: `PUT /api/v1/monitoring/alerts/{id}/resolve`)

## 4. 성공 기준

### 4.1. 기능적 기준
- 모든 시나리오가 100% 성공적으로 완료되어야 합니다.
- API 응답 시간이 500ms 이내여야 합니다.
- 데이터 정합성이 유지되어야 합니다.

### 4.2. 성능 기준
- 동시 사용자 100명 처리 시 에러율이 1% 미만이어야 합니다.
- 데이터베이스 연결 풀이 고갈되지 않아야 합니다.
- 메모리 사용량이 안정적으로 유지되어야 합니다.

### 4.3. 보안 기준
- 인증되지 않은 요청은 적절히 차단되어야 합니다.
- 민감한 데이터가 로그에 노출되지 않아야 합니다.
- SQL 인젝션 등 보안 취약점이 없어야 합니다.

## 5. 테스트 실행 환경

### 5.1. 환경 구성
- **프론트엔드:** React 애플리케이션 (localhost:3000)
- **백엔드:** FastAPI 서버 (localhost:8000)
- **데이터베이스:** PostgreSQL (localhost:5432)
- **Redis:** Redis 서버 (localhost:6379)
- **AI 에이전트:** 별도 컨테이너 (localhost:8001)

### 5.2. 테스트 도구
- **E2E 테스트:** Cypress 또는 Playwright
- **API 테스트:** Postman 또는 Newman
- **부하 테스트:** k6 또는 JMeter
- **모니터링:** Prometheus + Grafana
